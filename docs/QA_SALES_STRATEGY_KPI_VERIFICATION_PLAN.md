## 1. 施策別 KPI定義・計測手段・検証期間チェックリスト

各施策の効果測定を正確に行うため、KPI定義・計測手段・検証期間を明確化する。
計測ロジックのバグが売上数値を狂わせるリスクを排除することが本ドキュメントの目的。

---

### 施策① 無料トライアル → Premium転換

| 項目 | 内容 |
|------|------|
| **主要KPI** | トライアル開始数、有料転換率（CVR）、転換後MRR |
| **副次KPI** | トライアル離脱率、トライアル期間中の機能利用率 |
| **計測手段** | Stripe Subscription `status` フィールド (`trialing` → `active`) の webhook 監視 |
| **計測ポイント** | `checkout.session.completed` (トライアル開始), `customer.subscription.updated` (転換), `customer.subscription.deleted` (離脱) |
| **検証期間** | 実装後 14日間（7日トライアル × 2サイクル） |
| **目標値** | トライアル開始 100件/月、CVR ≥ 30%、MRR +¥150,000 |

**QA検証チェックリスト**:
- [ ] トライアル開始時に `subscriptionStatus = 'trialing'` がDB反映されること
- [ ] トライアル期限切れ時に自動で `active` or `canceled` に遷移すること
- [ ] 転換イベントがStripe webhook経由で正しくカウントされること
- [ ] 二重カウント防止（冪等性チェック）が機能すること
- [ ] トライアル→解約→再トライアルのエッジケースが正しく処理されること
- [ ] ダッシュボード上のCVR算出ロジック: `(active転換数 / trialing開始数) × 100`

### 施策② プロ・インフルエンサー招致

| 項目 | 内容 |
|------|------|
| **主要KPI** | 招致インフルエンサー数、インフルエンサー経由登録数、サロン/コーチング購入数 |
| **副次KPI** | インフルエンサー投稿エンゲージメント率、招致コスト単価 |
| **計測手段** | UTMパラメータ (`utm_source=influencer&utm_medium=referral&utm_campaign={name}`) + AffiliatePartnerモデルのトラッキング |
| **計測ポイント** | `affiliates` テーブルの `referralCode` 経由登録数、`tier = 'INFLUENCER'` フィルタ |
| **検証期間** | 実装後 30日間 |
| **目標値** | 10名招致、各50名登録 = 500名/月 |

**QA検証チェックリスト**:
- [ ] UTMパラメータが登録フローで保持・記録されること
- [ ] `AffiliatePartner.tier` が `INFLUENCER` のパートナー経由登録が正しくカウントされること
- [ ] インフルエンサー報酬率（50%）が正しく適用されること（通常30%と混同しないこと）
- [ ] 同一ユーザーの重複カウントが発生しないこと
- [ ] 報酬計算ロジック: `購入額 × 0.50` が正しいこと

### 施策③ 法人パートナーシップ（広告直販）

| 項目 | 内容 |
|------|------|
| **主要KPI** | 成約社数、広告収入合計（MRR）、広告CTR |
| **副次KPI** | アプローチ数、返信率、MTG設定率、継続率 |
| **計測手段** | 広告表示/クリックイベントのトラッキング（既存Ad system）、Stripe請求書ベース売上集計 |
| **計測ポイント** | `ads` テーブルの impression/click カウント、Stripe Invoice `paid` イベント |
| **検証期間** | 営業開始後 90日間（3ヶ月契約サイクル） |
| **目標値** | Month2: 1社成約 ¥30,000、Month3: 3社 ¥100,000 |

**QA検証チェックリスト**:
- [ ] 広告インプレッション・クリックカウントが正確に記録されること
- [ ] 広告CTR算出: `clicks / impressions × 100` が正しいこと
- [ ] Premium会員に広告が表示されないことが維持されること
- [ ] 広告枠別（サイドバー / フィード / パートナーページ）の分離集計が可能なこと
- [ ] 月次レポート用データが日次で蓄積されること

### 施策④ リファラルプログラム

| 項目 | 内容 |
|------|------|
| **主要KPI** | リファラルリンク生成数、リファラル経由登録数、リファラル経由有料転換数 |
| **副次KPI** | リファラルリンクシェア率、紹介者あたり平均獲得数 |
| **計測手段** | リファラルコード (`/signup?ref={code}`) のクエリパラメータトラッキング + DB記録 |
| **計測ポイント** | ユーザー登録時の `referralCode` 保存、紹介者IDとの紐付け |
| **検証期間** | 実装後 30日間 |
| **目標値** | リファラル経由登録 200名/月、有料転換 20名 |

**QA検証チェックリスト**:
- [ ] リファラルコード生成が一意であること（衝突テスト）
- [ ] リファラルリンク経由の登録で紹介者IDが正しく紐付けられること
- [ ] 自己紹介（自分のリファラルコードで自分が登録）が防止されること
- [ ] リファラル報酬（ポイント/割引）の付与が正しいタイミングで発生すること
- [ ] 報酬の二重付与が発生しないこと（同一被紹介者への重複防止）
- [ ] リファラル経由有料転換が正しくStripe subscriptionと紐付いてカウントされること

### 施策⑤ コンテンツSEO + SNS

| 項目 | 内容 |
|------|------|
| **主要KPI** | オーガニック流入数、SEO経由登録数、SNSシェア経由登録数 |
| **副次KPI** | ターゲットKW検索順位、ページ滞在時間、直帰率 |
| **計測手段** | GA4 イベントトラッキング (`utm_source=organic / note / youtube / x`)、OGPシェアカウント |
| **計測ポイント** | `utm_source` パラメータ別の登録コンバージョン |
| **検証期間** | 60日間（SEO効果の反映に2ヶ月想定） |
| **目標値** | オーガニック流入 1,000/月、登録転換率 5% = 50名/月 |

**QA検証チェックリスト**:
- [ ] UTMパラメータが全流入チャネルで正しく付与・記録されること
- [ ] GA4イベントとDB上の登録数に乖離がないこと（日次突合）
- [ ] OGP動的生成エンドポイントが正しい画像を返すこと（既存 `qa-stripe-e2e-test-scenarios.md` のOGP項目参照）
- [ ] SNSシェアボタンにUTMパラメータが自動付与されること
- [ ] note/YouTube外部記事からのリンクにUTMが正しく含まれること

## 2. Stripe連携 結合テスト項目（営業施策対応）

既存の `subscriptions.service.spec.ts`（28テスト）および `subscriptions.webhook.spec.ts`（4テスト）を基盤とし、営業施策に伴う新機能の結合テストを定義。

### 2.1 無料トライアル Stripe結合テスト

| ID | テストケース | 優先度 | 前提条件 | 期待結果 |
|----|------------|--------|---------|---------|
| ST-T01 | トライアル付きcheckout session作成 | P0 | 未課金ユーザー | `subscription.status = 'trialing'`, `trial_end` が正しい日時 |
| ST-T02 | トライアル期間満了→自動課金 | P0 | trialing状態のsubscription | `invoice.paid` webhook受信、`status = 'active'` に遷移 |

| ST-T04 | トライアル→課金失敗 | P1 | 期限切れカード | `invoice.payment_failed` 受信、`status = 'past_due'`、ユーザー通知 |
| ST-T05 | トライアル二重開始防止 | P0 | 既にtrialing中 | エラーレスポンス、二重subscription作成されない |
| ST-T06 | トライアル→解約→再トライアル | P1 | 過去にトライアル利用済み | ビジネスルールに従い許可/拒否（要仕様確認） |

## 3. テスト実行計画

### 3.1 テストフェーズ

| フェーズ | 対象 | 期間 | 完了基準 |
|---------|------|------|---------|
| **Phase A: 単体テスト** | 新規API・ロジック | 各施策実装完了後 3日以内 | P0テスト全件PASS |
| **Phase B: 結合テスト** | Stripe連携・トラッキング | Phase A完了後 5日以内 | P0/P1テスト全件PASS |
| **Phase C: KPI計測検証** | 計測ロジック正確性 | Phase B完了後 7日以内 | 既知データで算出値が期待値と一致 |
| **Phase D: 本番監視** | 各施策KPI | ローンチ後 14-90日 | KPI乖離率 < 5% |

### 3.2 テスト環境要件

- Stripe テスト環境（`sk_test_*` キー）でのwebhook動作確認
- Stripe CLI (`stripe listen --forward-to`) によるローカルwebhookテスト
- テスト用Priceオブジェクト（トライアル付き）の事前作成
- GA4 DebugViewでのイベント送信確認

### 3.3 リスク別テスト重点領域

| リスク | 影響 | 重点テスト |
|--------|------|-----------|
| トライアル→課金の二重カウント | MRR過大計上 | ST-T05, ST-T06 冪等性テスト |
| リファラル報酬の重複付与 | 不正損失 | ST-R06 冪等性テスト |
| インフルエンサー報酬率誤適用 | 収益損失 | ST-I01, ST-I02 tier分離テスト |
| UTMパラメータ欠落 | KPI計測不能 | 全施策のUTM保持テスト |
| 広告カウント不正確 | 営業報告の信頼性低下 | ST-A01〜A04 |
