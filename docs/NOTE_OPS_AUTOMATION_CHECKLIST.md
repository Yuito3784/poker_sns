# note連載 運用自動化・監視チェックリスト

## 概要
3日おき投稿サイクルを安定維持するための、Operations担当の自動化施策と監視ポイント。

---

## 1. リマインド自動化

### 1.1 Slack/Discord通知タイミング
| 通知タイミング | 対象者 | メッセージ内容 |
|--------------|-------|--------------|
| D-3 09:00 | CEO | 「記事#{No.}の構成・執筆を開始してください。テーマ: {テーマ名}」 |
| D-1.5 09:00 | CEO | 「記事#{No.}のドラフト提出期限です。本日中にドラフトを共有してください」 |
| D-1.5 18:00（未提出時） | CEO + Operations | 「記事#{No.}のドラフトが未提出です。エスカレーション検討」 |
| D-1 09:00 | QA/DevSecOps | 「記事#{No.}のレビュー期限は本日中です」 |
| D-0 09:00 | Operations | 「記事#{No.}の公開日です。公開チェックリストを実行してください」 |
| D+1 10:00 | Operations | 「記事#{No.}の初動KPI計測を実施してください」 |

### 1.2 実装方法（推奨）
- **Slack Workflow Builder** または **Zapier/Make** でスケジュールトリガー設定
- スプレッドシートの公開予定日カラムをトリガーソースとして連携
- 代替: Google Apps Script で定時実行 → Slack Incoming Webhook

---

## 2. 投稿サイクル監視

### 2.1 遅延検知ルール
| 監視項目 | 閾値 | アクション |
|---------|------|----------|
| ドラフト提出遅延 | D-1.5 EOD未提出 | CEOへ直接リマインド + 翌朝までの猶予通知 |
| レビュー遅延 | D-0.5 EOD未完了 | レビュー担当へ催促 + 公開1日延期検討 |
| 公開遅延 | D-0 15:00未公開 | Operations内でバッファ記事公開を判断 |
| 2回連続遅延 | - | 投稿頻度を4日おきへ一時緩和提案 |

### 2.2 ステータス監視ダッシュボード
管理ボード（CSV/スプレッドシート）を定期確認し、以下を週次で報告:
- 今週の公開予定記事とステータス
- 前週の公開記事の初動KPI
- バッファ記事ストック残数
- 遅延・エスカレーション発生状況

---

## 3. KPI自動集計

### 3.1 note Analytics連携
- noteのクリエイターページから手動取得（API非公開のため）
- 取得項目: PV、スキ数、コメント数
- 記録先: 管理ボードの各記事行

### 3.2 poker_sns流入計測
- note記事内のpoker_snsリンクにUTMパラメータを付与
  - `?utm_source=note&utm_medium=article&utm_campaign=article_{No.}`
- Google Analyticsまたはサーバーログで流入数を計測
- 週次で管理ボードへ反映

### 3.3 月次レポート項目
| 指標 | データソース | 目標値 |
|------|------------|-------|
| 月間投稿数 | 管理ボード | 10本 |
| 月間総PV | note Analytics | 1,000+ |
| 平均スキ率 | note Analytics | 2%+ |
| poker_sns流入 | UTM計測 | 月30+ |
| noteフォロワー増 | note Analytics | 月+50 |
| 有料記事売上 | note売上管理 | （段階的に設定） |

## 4. 品質維持の自動チェック

### 4.1 文字数カウント
- ドラフト提出時に自動で文字数カウント（3000〜5000字の範囲チェック）
- 範囲外の場合は執筆者へ自動通知

### 4.2 リンク死活監視
- 公開済み記事内のリンク（poker_snsへのリンク含む）を週次でチェック
- 404検出時にOperationsへアラート

### 4.3 SEO基本チェック（公開前）
- [ ] タイトルに主要キーワードが含まれているか
- [ ] 見出し構成が論理的か（H2/H3の階層）
- [ ] 内部リンク（過去記事・poker_sns）が適切に設置されているか
- [ ] ハッシュタグが5個以上設定されているか

---

## 5. インシデント対応手順

### 5.1 記事内容に問題発覚（公開後）
1. 問題箇所を特定（セキュリティ情報漏洩 / 事実誤認 / 権利侵害）
2. セキュリティ関連: 即座に記事を非公開化 → DevSecOpsへ報告
3. その他: 修正版を準備 → 修正公開 → SNSで訂正告知

### 5.2 noteプラットフォーム障害
1. note公式Twitterで障害情報を確認
2. 公開作業を復旧まで保留
3. 復旧後に通常フローで公開
