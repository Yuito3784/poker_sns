# Stripe 本番環境登録 — セキュリティ・チェックリスト対応

クレジット取引セキュリティ対策協議会のセキュリティ・チェックリストに基づく、本プロジェクトの該当状況と推奨対応です。Stripe 本番登録時の「セキュリティ対策について」「導入方法」の回答にそのまま使えます。

---

## 1. 導入方法の回答

| 質問 | 推奨回答 |
|------|----------|
| **どのように決済を行いますか？** | **その他 (例えば、Stripe Checkout や Payment Element)** |
| **商品やサービスをオンラインで販売していますか？** | **はい** |

**根拠**: 本プロジェクトでは以下を利用しています。

- **Stripe Checkout**: サブスク（`subscriptions`）、サロン加入（`salons`）
- **Stripe Payment Intents**: チップ（`tipping`）、有料コンテンツ（`paid-content`）、大会参加費（`tournaments`）、コーチング予約（`coaching`）
- **Stripe Billing Portal**: サブスク解約・支払い方法変更

## 2. チェックリスト項目ごとの該当状況と対策

### 2.1 管理者画面のアクセス制限と ID/PW 管理

**重要**: 管理者アカウントがあります（`ADMIN_USER_IDS` で指定したユーザーが API 上で管理者扱い）。  
「該当なし: 管理者アカウントはありません」は選べません。

| 項目 | 現状 | 推奨対応 |
|------|------|----------|
| **IP 制限 or ベーシック認証** | 未実装。JWT による「管理者ユーザーかどうか」の判定のみ（`AdminGuard`）。 | 本番では次のいずれかを推奨。<br>・**推奨 A**: 管理者用 API を叩ける IP をファイアウォール/Reverse Proxy（Cloudflare、AWS WAF 等）で制限。<br>・**推奨 B**: 管理者向けルート（例: `/salons` の管理系、`/affiliates/admin/*`、`/earnings`）の前にベーシック認証や VPN を配置。 |
| **二段階認証 / 二要素認証** | 未実装。管理者も一般ユーザーと同じログイン（メール/パスワード or OAuth）。 | 管理者ユーザーには、ログイン後の 2FA（TOTP 等）を導入するか、少なくとも「管理者は Google/LINE/X 等の OAuth のみに統一し、パスワードログイン不可」とする運用を推奨。 |
| **ログイン失敗でアカウントロック（10 回以下）** | 未実装。`User` に `loginAttempts` / `lockedUntil` なし。Throttle のみ（IP あたり 10 回/分）。 | **必須に近い**。`docs/phase4-implementation-spec.md` の「4-1-1 アカウントロックアウト」を実装し、**10 回以下**でロック（例: 5 回失敗で 15 分ロック）にするとチェックリストに合致。 |

**Stripe 登録時の記入例**（文言は調整可）:

- IP 制限 or ベーシック認証: 「本番環境では管理者向け API へのアクセスを Cloudflare（または ○○）で許可 IP に制限予定。開発中は ○○ で対応予定。」
- 二段階認証: 「管理者は OAuth ログインに限定し、パスワードログインを無効化予定。または TOTP 二要素認証を導入予定。」
- アカウントロック: 「ログイン失敗回数に応じたアカウントロック（○回で○分）を Phase4 で実装予定。」

|------|------|------|

| **アップロード可能な拡張子・ファイル制限** | アバター・投稿画像等のアップロードがあり、バリデーション実装済み。 | **はい** で回答可能。 |

### 2.6 不正ログイン対策（会員ログインあり）

会員ログイン機能があるため「該当なし: 会員のログイン機能はありません」は不可。

| 対策 | 現状 | 対応 |
|------|------|------|
| **ログイン試行回数の制限とスロットリング** | `@Throttle` によりログイン API は 10 回/分に制限済み。 | **はい** で回答可能（「ログイン試行回数の制限とスロットリング」にチェック）。 |

追加で、**アカウントロック**（2.1 と同様）を実装すると、チェックリスト上はより明確です。

## 3. 本番登録前に確認したい技術ポイント

- **Stripe Webhook の raw body**  
  - 現在、`main.ts` で `express.raw()` を指定しているのは `/subscriptions/webhook` のみ。  
  - 他の Stripe Webhook（`/salons/webhook`, `/paid-content/webhook`, `/tipping/webhook`, `/tournaments/webhook`, `/coaching/webhook`）も、署名検証のために **raw body** で受け取る必要があります。Nest の `rawBody: true` で他ルートに raw が渡っているか、または各 Webhook パスに同様の `express.raw()` を適用しているかを確認してください。

- **本番用環境変数**  
  - `STRIPE_SECRET_KEY` → `sk_live_*`  
  - `STRIPE_WEBHOOK_SECRET` → 本番用 Webhook の `whsec_*`（Dashboard で本番用エンドポイント作成後に取得）  
  - サロン・チップ等で別 Webhook を使う場合は、対応する `STRIPE_*_WEBHOOK_SECRET` も本番用に切り替え。

- **CSP**  
  - `frameSrc` に `https://js.stripe.com` が含まれており、Stripe Checkout / Payment Element 利用に支障ない構成です。

## 4. 回答まとめ（Stripe 画面への入力用）

- **導入方法**: その他（Stripe Checkout・Payment Element）
- **商品・サービスのオンライン販売**: はい
- **1. 管理者画面**
  - IP 制限 or ベーシック認証: 本番で IP 制限またはベーシック認証を導入予定である旨を記載。
  - 二段階認証: OAuth 限定 or TOTP 導入予定である旨を記載。
  - アカウントロック: ログイン失敗 N 回でロックする機能を実装予定である旨を記載（Phase4 等）。
- **2. データディレクトリ**: 重要なファイルは公開ディレクトリに置かない・アップロード拡張子制限 — **はい**
- **3. 脆弱性対策**: 診断・SQL/XSS 対策・セキュアコーディング — **はい**
- **4. マルウェア対策**: 本番・開発環境で実施予定 — **はい**
- **5. 有効性確認・クレジットマスター対策**: Stripe の制限を利用 — **はい**
- **6. 不正ログイン対策**: ログイン試行回数の制限とスロットリング — **はい**（該当なしは不可）

上記のとおり、「管理者の IP 制限 / 2FA / アカウントロック」を「予定」として明記し、それ以外は現状で「はい」で揃えられます。アカウントロックは Phase4 仕様に沿って実装すると、チェックリストとの整合が取りやすくなります。
