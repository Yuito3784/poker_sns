## 1. エラー発生時の標準対応手順 (SOP)

### 1.1 今回のエラー分析

| 項目 | 内容 |
|------|------|
| エラー種別 | `model_not_supported` (HTTP 400) |
| 発生レイヤー | Climpireプラットフォーム (エージェント間API呼び出し) |
| 原因 | Copilot APIに未対応のモデルIDが指定された |
| 影響範囲 | 該当タスクの実行停止のみ。poker_snsアプリ本体には影響なし |
| 解決策 | モデルID差し替え (`claude-sonnet-4-6` 等の対応モデルへ変更) or 担当再割り当て |

### 1.2 エラー分類と対応フロー

```
エラー発生
  |
  +-- [Lv1] 環境/インフラエラー (model_not_supported, timeout, 503等)
  |     -> 即時: CEOまたはPlanningがタスク再割り当て or パラメータ修正
  |     -> 目標対応時間: 30分以内
  |
  +-- [Lv2] 実装エラー (ビルド失敗, テスト失敗, 型エラー等)
  |     -> 即時: 担当開発チームが修正、QAが再検証
  |     -> 目標対応時間: 2時間以内
  |
  +-- [Lv3] 設計/要件エラー (仕様不整合, 依存関係衝突等)
  |     -> 即時: Planningがインパクト分析、CEO判断をエスカレート
  |     -> 目標対応時間: 半日以内
  |
  +-- [Lv4] 外部依存エラー (Stripe API障害, 外部サービスダウン等)
        -> 即時: DevSecOpsがステータス確認、代替策をPlanning起案
        -> 目標対応時間: 外部復旧待ち + 社内対応1時間以内
```

### 1.3 CEOの役割 (今回の依頼への回答)

CEOが行うべきアクションは以下3点:

| # | アクション | タイミング | 具体内容 |
|---|-----------|-----------|---------|
| 1 | ブロッカー判断 | エラー報告受領後即時 | エラー該当タスクを「再割り当て」か「修正して再実行」か判断 |
| 2 | 優先度トリアージ | 週次 or 受信箱8件以上時 | 収益影響度順にタスクの優先順位を決定 |
| 3 | 売上KPI監視 | 週次 | Phase別目標達成率を確認し、ボトルネックにリソース再配分 |

**今回の具体対応**: `model_not_supported`エラーのタスクは、Climpireプラットフォーム側のモデルID設定を対応モデル(`claude-sonnet-4-6`)に差し替えるか、手動で対応可能な担当者に再割り当てすれば即解消。

## 3. 売上100万円 ロードマップとの接続

エラーハンドリング強化は直接収益を生まないが、以下の経路で売上目標に貢献:

```
エラー早期検知 → MTTR短縮 → サービス稼働率99.5%+
  → ユーザー信頼 → 解約率低下 → LTV向上
  → 月100万円の維持に必要な基盤
```

| 売上ロードマップPhase | 必要なサービス品質 | 今回の施策の貢献 |
|---------------------|-------------------|----------------|
| Phase 0: 公開基盤 | デプロイ安定性 | CI/CD通知で即検知 |
| Phase 1: 初期収益化 | 課金フロー安定 | Webhook失敗通知 |
| Phase 2: 成長加速 | DAU維持 | エラーバナーUXでユーザー離脱防止 |
| Phase 3+: スケール | SLA維持 | ヘルスチェック + ランブック |

## 4. リスクと対策

| リスク | 確率 | 影響 | 対策 |
|--------|------|------|------|
| Slack Webhook設定ミス | 中 | 通知漏れ | テスト用チャンネルで事前検証 |
| ExceptionFilter変更によるパフォーマンス低下 | 低 | レスポンス劣化 | 非同期通知、バッチ送信 |
| 外部モニタリングサービスの費用超過 | 低 | コスト増 | 無料枠内 (UptimeRobot等) で運用 |
| エラーバナーUIが過剰表示されUX劣化 | 中 | ユーザー離脱 | 表示条件にdebounce (30秒) 設定 |
