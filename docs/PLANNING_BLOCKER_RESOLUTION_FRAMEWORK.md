# ブロッカー解消・自律タスク進行フレームワーク

**作成日**: 2026-03-02
**作成者**: Planning (常闇)
**ステータス**: Active
**対象**: 全チームリーダー

---

## 1. 目的

タスク遂行中にブロッカーが発生した際、30分以内に原因特定し、自律的に次タスクへ移行する。CEOの意思決定が必要な場合のみエスカレーションする。

---

## 2. ブロッカー分類と判断基準

### Level 1: 自己解決（即時〜30分）

| 種別 | 具体例 | 対応方法 |
|------|--------|---------|
| 技術的障壁 | ビルドエラー、依存関係の不整合 | ログ確認→修正→次タスクへ |
| 情報不足 | 仕様の不明点 | 既存ドキュメント参照→推定実装→後からレビュー |
| 環境問題 | Docker起動失敗、ポート競合 | 再起動→別手段→スキップして次へ |
| 軽微な設計判断 | 変数名、ファイル配置 | チーム規約に従い自己判断 |

### Level 2: チーム間調整（30分〜2時間）

| 種別 | 具体例 | 対応方法 |
|------|--------|---------|
| 他チーム成果物待ち | テンプレート未完成でレビュー不可 | 並行可能な別タスクへ切替 |
| API仕様の不一致 | フロント↔バック間の型ずれ | 暫定型で進行→結合時に修正 |
| レビュー待ち | PRが承認待ち | 次のPR作成に着手 |

### Level 3: CEO判断必須（エスカレーション）

| 種別 | 具体例 | エスカレーション方法 |
|------|--------|-------------------|
| 予算決定 | VPS契約、有料API課金 | 選択肢+推奨案をMDに記載→CEO通知 |
| 外部契約 | アフィリエイト提携先の最終決定 | 候補リスト+比較表をMDに記載→CEO通知 |
| 方針変更 | ターゲット市場の変更、機能削除 | 影響分析をMDに記載→CEO通知 |
| 法的リスク | 賭博法関連の判断 | リスク評価をMDに記載→CEO通知 |

## 3. タスク切替プロトコル

### 30分ルール

```
ブロッカー発生
  ↓
[0〜10分] 原因特定を試みる
  ↓
  ├─ 解決 → 続行
  │
  └─ 未解決
      ↓
[10〜20分] 代替アプローチを試す
      ↓
      ├─ 解決 → 続行
      │
      └─ 未解決
          ↓
[20〜30分] ブロッカーを記録し、次タスクへ切替
          ├─ Level 1/2 → 自律切替（記録のみ）
          └─ Level 3 → CEO通知 + 次タスクへ切替
```

### 切替先タスクの優先順位

1. **同フェーズ内の未着手タスク** — 依存関係のないもの優先
2. **次フェーズの先行着手可能タスク** — 調査・設計フェーズ
3. **ドキュメント整備** — 既存タスクの仕様書・手順書作成
4. **技術的負債の解消** — テスト追加、リファクタリング

## 4. ブロッカー記録フォーマット

ブロッカー発生時、`docs/blockers/` 配下にMDファイルで記録する。

### ファイル名規則
`YYYY-MM-DD_[チーム略]_[概要].md`

例: `2026-03-02_plan_theme-list-ceo-approval.md`

### 記載項目

```markdown
# ブロッカー記録

- **発生日時**: YYYY-MM-DD HH:MM
- **チーム**: Planning / Development / Design / QA / DevSecOps / Operations
- **担当者**: (名前)
- **ブロッカーレベル**: Level 1 / 2 / 3
- **概要**: (1行で)
- **詳細**: (原因と試したこと)
- **切替先タスク**: (何に切り替えたか)
- **解消条件**: (何が揃えば元タスクに戻れるか)
- **ステータス**: Open / Resolved
- **解消日時**: (解消時に記入)
```
